Spec-Driven Design

Spec-Driven Design

Sep 12, 20266 min read

  • software-design
  • ai
  • workflow

When I was vibe-coding a project for a hackathon (as one is allowed to do), I felt like the software we were building broke down quickly (go figure). I was on a team of four people and we were shipping tons of features within a short amount of time. We kept coming across:

  • Code conflicts
  • Agents making assumptions about our intent
  • Stale code being left behind
  • Difficulty reconciling features

Obviously vibe-coding is going to break down quickly; that’s the trade-off. You test a bunch of ideas and see what sticks, but the code is disposable. This project got me thinking: when building mature software, how do we better plan and execute designs with agents?

I started testing written “contracts”. A contract gives a clear definition of how components will interact with one another. I begin the process with a prompt outlining what I want to build: goals, non-goals, and core features. From there, I have the agent scaffold a spec Markdown file using a template that I prepared. I iterate on this spec until the agent and I are aligned.

The specification (spec) doc looks a lot like a lightweight product requirements document (PRD) or technical design document. I review it several times, catch bad assumptions, and trim flawed ideas before any code is created. Once the requirements and boundaries are clear, I let the agent start implementation.

Greenfield vs. Mature Software Projects

A spec’s shape (and scope) will shift depending on where the software is in its lifecycle:

  • For brand-new software, the first spec will naturally have a broad scope of information. You’ll be defining domain models, foundational architecture, and core conventions from scratch.
  • For mature systems, the spec becomes more focused. The point of it shifts from exploring foundational aspects of the system to defining the specific new features. You’ll be documenting migration sequences, failure planning, backwards compatibility, and regression boundaries.

Anatomy of a Spec

A spec doesn’t need to be a 20-page document. It only needs enough structure to eliminate the ambiguity where agents typically wander off course.

I like to include these sections:

  • Context / Problem Statement
    • Contracts and endpoints explain what to build, but not why. Agents need context to solve the problem correctly.
  • Goals and Non-Goals
    • Agents love to add “helpful” functions, extra config flags, and unprompted refactors. Clear goals define what success looks like; non-goals tell the agent what not to touch.
  • Component Contracts and Interfaces
    • Defines how components communicate with one another.
    • Can include things like:
      • Function names, params, return values
      • API routes, request and response schemas
      • Database schemas
    • These fixed boundaries help keep agents from inventing arbitrary data structures.
  • Failure Planning and Edge Cases
    • Agents default to naive error handling unless instructed otherwise. This section documents:
      • Expected failure modes (timeouts, network drops, malformed input)
      • How errors should bubble up, log, or alert
      • Fallbacks, retries, and rate limits
  • Migration and Compatibility
    • For established software, this section defines the blast radius of the change, including:
      • Schema migrations and seed data
      • Breaking changes or deprecation plans
      • Rollback steps if the deployment fails
  • Constraints and Approved Dependencies
    • This section states which tools, libraries, or patterns must be used. Agents love installing whatever package they find to solve trivial problems, or pulling in a bloated framework when a short utility function was all you needed.
  • Acceptance Criteria
    • A checklist of testable/falsifiable requirements. This gives you and the agent the definition of “done”.

Pros and Cons

Pros

  • Cheaper and faster than unwinding code: If a design is wrong, you can’t just delete the code. You have to rip out tests, package imports, doc updates, and helper libraries. Iterating in Markdown avoids that churn entirely.
  • Prevents agents from guessing system architecture: Specs force key decisions (libraries, schemas, contracts) to be locked down before code is generated.
  • Prevents context drift across sessions: When constraints are omitted, an agent invents its own. Two different agents (or two separate chat sessions) will make conflicting choices unless anchored by the same written “contracts”.
  • Helps prevent scope creep: Explicit goals, non-goals, and acceptance criteria give both you and the agent an unambiguous definition of done.
  • Durable decision records: Months later, the spec explains why an approach was chosen and what alternatives were rejected at the time.

Cons

  • Spec drift: Reality changes during implementation. If you hit an edge case and fix it only in code, the spec becomes stale unless you maintain the discipline to update it.
  • Risk of over-engineering: Writing an exhaustive spec for an exploratory prototype or hackathon project is wasted overhead if the code gets thrown away.
  • Front-loaded friction: You have to sit and think through contracts, edge cases, and interfaces before writing any code.

Fighting Spec Drift

When implementation reveals an unexpected edge case, resist the temptation to just patch the code. Update the spec first, agree on the design adjustment, and only then write the code. The document must remain the single source of truth.

Future

Currently, I’m investigating:

  • How can I better manage the state of my implementation repo with what’s in my docs repo?
    • Implementation repo changes require manual updates to docs.
    • Spec files are getting too large with historical records and changes.
    • Organizing and keeping track of different work streams is difficult.
  • How can I offload context needed for agents to properly update relevant docs?
    • How can I move agent prose into deterministic code?
  • It’s hard to balance where information lives. (gotchas, historical records, knowledge, plans)
  • Using frontmatter seems necessary and helpful for doc maintenance.
    • How could I utilize commit shas to track docs? 🤔
  • Orchestrating multiple agents at a time. Essentially DeepAgents, but my own version, with less batteries included, but using my subscriptions.

Closing

I’m curious what others out there are doing with agentic workflows and documentation. This spec-driven design is just something I’ve found to be helpful in my day to day use of LLMs. I’ll continue evolving this design as I scale my agentic workflows.

Overall, I’ve noticed this spec workflow tends to drift and bloat more when adding more agents to the equation.

I’ve also found myself asking “is this even solving the correct problem?” after getting deep into a spec… This is why PRDs are important.

Besides that, it’s been working well, especially for more mature software systems that already have a lot of context and documentation.

I do treat specs as likely untrustworthy, since they’re largely LLM generated. Don’t sell to others that this is a source of truth file.
