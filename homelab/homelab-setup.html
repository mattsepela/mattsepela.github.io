Homelab setup

Homelab setup

Sep 02, 20266 min read

  • homelab
  • kubernetes

My homelab runs the services my household depends on1, and it’s where I learn infrastructure by breaking it. The rule I hold it to is cattle, not pets: every node is disposable, and the whole cluster is declarative enough to rebuild from Git.

It started as Proxmox VMs and Docker Compose stacks. It now runs as a bare-metal, three-node Kubernetes cluster on Talos Linux, with every piece of desired state living as text in Git.

Each runs in its own namespace with resource limits and a default-deny NetworkPolicy.

Why Talos

Most distributions hand you a shell and trust you not to break things. Talos removes the ways you’d normally log into a box and change it by hand:

  • no shell
  • no SSH
  • no package manager
  • a read-only root filesystem

The only way to change a node is to send it a new machine configuration over its API.

That sounds restrictive, but it’s really the “declared state” principle applied to the OS itself. No snowflake nodes, because there’s no way to hand-tweak one:

  • A node is fully described by its config, generated from the repo by talhelper.
  • Adding the zfs kernel module is a patch, not modprobe.
  • Reading kernel logs is talosctl dmesg, not SSH.

I don’t fix a node, I re-declare and re-apply it.

The security payoff is real but bounded. That immutability raises the cost of persistence after a compromise, but it does not stop initial node-root access. That’s part of why Tetragon exists below.

Why Cilium

Cilium is the cluster CNI, running as a full eBPF kube-proxy replacement. It’s worth the complexity for consolidation.

I have one data plane that:

  • moves pod traffic
  • hands out LAN LoadBalancer IPs via L2 announcements
  • enforces NetworkPolicy
  • surfaces every network flow through Hubble

The alternative was a pile of smaller parts: kube-proxy plus MetalLB plus a separate policy engine. Cilium does all of it with the one agent pod networking already requires, so LoadBalancer support was a config change, not a new component.

Every namespace ships with a default-deny NetworkPolicy and a narrow allowlist. Hubble is what makes that maintainable. When a flow is denied I can see the drop instead of guessing what’s actually talking to what.

Why Tetragon

Talos forwards kernel audit logs, so I already had process-execution telemetry. The gap is identity: those records carry pid / uid / comm / exe but nothing about Kubernetes. “Which process ran” without “in which pod” is a much weaker answer for a Kubernetes-native threat model.

Tetragon is Cilium’s eBPF runtime security agent. It closes that gap. Every event natively carries pod / container / namespace identity and process ancestry across exec chains. It also drops into the existing pipeline with no new plumbing, since events go to stdout and Vector already tails that into ClickHouse.

The catch is enforcement. Tetragon can kill a process or block a syscall, not just record it, and that happens in-kernel the moment a policy matches. There is no admission webhook, no gradual rollout, no “it’ll heal on the next reconcile.” So I run it observe-only, and do not ship a TracingPolicy without intense review. 😅

Networking and edge

Segmentation happens in two places: at the gateway, and again inside the cluster. Default-deny is the baseline in both.

  • Gateway:
    • UniFi Cloud Gateway routes between VLANs (LAN, Server, IoT, Guest) behind a zone-based firewall
    • inter-VLAN traffic is default-deny, only required flows allowlisted
    • UniFi switches and APs carry the tagged networks
  • DNS (Blocky):
    • three replicas behind one VIP with automatic failover
    • split-horizon resolution for local zones
    • network-wide ad blocking
    • DoT / DoH upstream
  • Remote access (Tailscale):
    • the Tailscale operator exposes selected services to the tailnet by name with managed HTTPS
    • no open inbound ports 2
  • TLS (Caddy):
    • each service runs its own Caddy sidecar terminating HTTPS with Let’s Encrypt certs
    • LAN and Tailscale-only services share one domain
    • internet-facing services use a separate domain behind a shared wildcard cert

Observability

Everything logs somewhere I can query. The pipeline is self-hosted end to end, partly because I want the data and partly because building the detection side is the security work I actually enjoy:

  • Vector tails Talos host logs, container stdout/stderr, and the UniFi gateway’s firewall events.
  • ClickHouse stores all of it as columnar tables. Detection rules run as scheduled queries against those tables and post enriched alerts to Discord.
  • VictoriaMetrics keeps the metrics, held long enough to know what each workload’s normal looks like.
  • Grafana sits on top for dashboards and alerting.

Storage and backups

Anything that needs a volume gets one from the nodes’ NVMe ZFS pools through OpenEBS ZFS-LocalPV, so no workload is pinned to a host path I mounted by hand. Stateful data snapshots on a schedule and syncs offsite, encrypted.

That’s the short version. Backup and recovery is the part I’ve thought about most, so it gets its own note later.

Footnotes
