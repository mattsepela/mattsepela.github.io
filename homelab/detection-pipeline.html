Detection pipeline

Sep 13, 202615 min read

  • homelab
  • security
  • kubernetes

My observability pipeline collects logs from containers, hosts, and network flows in ClickHouse. The detection pipeline builds on that: it runs scheduled SQL queries against those logs and sends matches to Discord.

Hardening comes first, but a misconfiguration, zero-day exploit, or supply chain attack can still get an attacker past preventative controls. Monitoring for malicious activity gives me a chance to spot that and respond. tl;dr: defense in depth.

I enjoy this part of security. This design is still a WIP, and I’m working on its features, reliability, and efficiency.

Why a custom orchestrator?

I didn’t start here. My first detections ran as Grafana alert rules against ClickHouse, and that worked until it didn’t.

Grafana tracks alert state, but my queries had no persistent record of which logs they had checked. Every evaluation re-ran a sliding window like Timestamp > now() - INTERVAL 15 MINUTE. Short gaps were fine, because each event got several chances to be seen. After a gap longer than the window, the next evaluation skipped the older events. I needed a cursor that could resume from the last successful query.

I found that out the hard way. Re-running my ClickHouse bootstrap job ran CREATE USER OR REPLACE, which silently dropped the grants Grafana’s user depended on. Detections were blind for an entire day. The logs were still there, but checking what the rules missed meant manually re-running the queries over that gap. The bootstrap job still recreates users, but every grant now lives in the same script, right after the user it belongs to, so a re-run restores them.

I looked at the alternatives before writing any code:

  • Wazuh, Security Onion, Elastic Security: I was looking for a runner for my existing ClickHouse queries. Adopting a full security platform would mean another ingestion path and datastore to maintain, plus adapting the detections to that platform.
  • Sigma plus a ClickHouse backend: Sigma is a good format, but the only ClickHouse backend I found was a dormant hobby project. It’s also just a compiler, so something still has to run the query and track state.
  • ElastAlert2: exactly the right shape of tool, but built for Elasticsearch.
  • Kestra or another Airflow-style scheduler: it can re-run jobs it missed, but it tracks when a job was supposed to run, not which logs have actually been checked. I’d still have to write the cursor logic myself, and I’d be running a new service with its own database just to start the job.

A small runner on the store I already had won every comparison. It borrows ideas instead of platforms:

  • a persistent cursor with a buffer for late logs
  • an outbox, so delivery is separate from detection
  • retries with exponential backoff
  • honoring Retry-After when rate limited
  • a dead-letter state for alerts that keep failing

My first version ran each detection as its own CronJob. That needed a lock so the same detection never ran twice at once, and the lock was a Kubernetes Lease, which meant giving every detection pod permission to talk to the Kubernetes API. It also broke. All the detections shared one ClickHouse user with a limit of five simultaneous queries, and in one minute, eight of them started together and every one crashed.

Now one pod runs every detection, one after another. Most queries take a millisecond or two and the slowest about a tenth of a second, so the whole sweep finishes in about two seconds. Running them in order removed the contention between those detections, and the lock, its permissions, and the pods’ Kubernetes access all got deleted. Also my server fans don’t spin up every time my detections run… 😅

Every detection is a YAML file with a name, a severity, and a SQL query. The orchestrator is about 700 lines of Python in one container image, run as two CronJobs that share it:

  • detection-sweep runs every five minutes. One pod runs every detection serially and writes matches to an outbox table.
  • detection-drain runs every minute. It posts anything in the outbox that hasn’t been delivered yet.

Neither pod has a Kubernetes ServiceAccount token. The sweep only talks to ClickHouse, and the drain is the only pod that holds the Discord credentials.

Each CronJob uses concurrencyPolicy: Forbid to skip a scheduled run while its previous Job is active. The sweep and drain can still run alongside each other. This removes ordinary overlap within each job, but CronJob scheduling is approximate, so repeated execution still needs to be safe.

The cursor

Each detection keeps a cursor in ClickHouse: the timestamp it has queried through. One run looks like this:

  1. Read the detection’s cursor.
  2. Ask ClickHouse for the current time and subtract a three-minute lag buffer. That’s the end of the window.
  3. Run the detection’s SQL over everything after the cursor, up to the end of the window.
  4. Insert every match into security.detection_results as pending.
  5. Move the cursor to the end of the window.

The cursor advances only after all matches have been saved. If the run fails before that advance, the next run starts from the same spot. When I accidentally broke the pipeline for an hour, turning it back on caught every event it had missed.

A few details it took an incident or two to get right:

  • ClickHouse’s clock, not the pod’s. The window end comes from SELECT now64(), so clock skew between a pod and the database can’t open a gap.
  • The lag buffer. Logs don’t land in ClickHouse the instant they happen. Stopping three minutes short of now gives them time to arrive before their timestamps are queried.
  • A capped window. After an outage, a detection doesn’t try to query the whole gap at once. Each run covers at most six hours past the cursor, to limit the amount of work attempted in one query. A busy six-hour window can still hit the query timeout or the pod’s memory limit.

This catches up after the runner stops, as long as the logs are still retained. It does not recover every late arrival: if a log lands after the cursor has already passed its timestamp, the normal sweep misses it. The three-minute buffer reduces that risk; it does not eliminate it.

The outbox

An outbox works like the one in your email client. You write the message down first, and something else sends it later. If sending fails, the message is still there waiting.

My first version didn’t work that way. One run did everything in order:

  • query -> save matches -> post to Discord -> move cursor

The cursor only moved once Discord accepted the alert. That seemed like a reasonable way to never lose an alert. My thinking was: if Discord is down, the cursor stays put and the next run tries again.

The catch was that the next run doesn’t just retry the post. It redoes the whole run (query, save, post, move), including the parts that already went through, so alerts that already landed in Discord got posted again.

The fix was splitting that run into two jobs that don’t wait on each other:

  • sweep: query -> save matches as pending -> move cursor
  • drain: find pending matches -> post to Discord -> mark sent

The sweep doesn’t care whether Discord is up. It saves matches as pending before moving the cursor, so delivery can continue separately. The drain works through that queue and retries individual delivery steps. In the first version, one retry wrapped around all three Discord calls: a bad bot token posted the alert three times and never delivered the payload.

Retrying individual steps avoids repeating work whose success has been recorded. It does not guarantee duplicate-free delivery. If Discord accepts a post and the drain crashes before recording that success, a retry can post it again.

ClickHouse, like most OLAP databases, is built for inserts, and updating rows in place is expensive, so I don’t do it. Each status change inserts a new copy of the row, identified by a hash of the detection and the matched data. The ReplacingMergeTree engine consolidates those copies during background merges. Until then, several versions can coexist. Reads need to resolve the latest state, using FINAL or an equivalent latest-version query, before deciding which matches are pending; the engine alone does not guarantee that. A nice side effect: the orchestrator’s database account can insert rows, but it has no permission to modify or delete them. 😄

There is another way to get a duplicate today. If the sweep saves matches but fails to advance its cursor, the drain can deliver them before the next sweep retries that window. The repeated sweep inserts those matches as fresh pending rows with a newer updated_at, so they can replace the sent state and be delivered again. The match hash keeps their identity stable; it does not preserve their delivery state across a repeated sweep.

What a detection looks like

Detections are plain YAML files, shipped to the pods as a ConfigMap. A generator checks the required fields at apply time, so a malformed file fails before it ever reaches a pod. Adding a detection is adding a file.

SEC-002 is my favorite because its baseline is so clean. Every one of the exec, attach, and port-forward requests in my K8s audit history came from my own admin identity. A ServiceAccount doing it is worth a look:

Each field has a job:

Tuning

Tuning goes wrong in both directions. Under-tune and a rule drowns you in noise until you stop reading it. Over-tune and it goes quiet on exactly the thing it was written for.

SEC-007 did both. Untuned, it fired on Jellyfin shells, so I excluded the whole Jellyfin workload. When I went back to check, every one of those shells was me running kubectl exec to debug, and Jellyfin had never started a shell itself. The exclusion was hiding the one shell SEC-007 exists to catch: the one a compromised Jellyfin would start. 🤦 Now it only skips a Jellyfin shell when the Kubernetes audit log shows a kubectl exec that opened it: same pod, same container, same command, with an identity tied to me that occurred within a few seconds. The rule of thumb: an exclusion should be exactly as wide as the evidence behind it.

Response workflow

Once the sweep saves a match, a Discord alert lands within about a minute. Counting the three-minute lag buffer and the five-minute sweep, that’s roughly four to nine minutes from the event itself. The alert has three parts:

  1. The embed: detection name, description, ID, severity, and match count.
  2. A thread on that message, named after the detection.
  3. payload.json in the thread, holding the matched rows.

The payload is always a file attachment, never a code block. Matched rows contain attacker-influenced text, like the arguments of a process that just tripped a detection. A backtick in those arguments could break out of a code fence and inject Markdown into the alert, including @everyone. Discord never parses an attachment as Markdown, and mentions are disabled on every message anyway.

The delivery path taught me another lesson: a webhook URL is a credential. A transient DNS failure made requests print the full Discord webhook URL, token included, into an exception. That traceback went to pod logs, which my own pipeline then shipped into ClickHouse. Errors are redacted now and re-raised without the original exception chained.

From here, I’ll typically investigate by running SQL queries against ClickHouse, but let’s be real, I’m not trying to be on-call all day, so my buddy Claude runs some queries for me.

Watching the watcher

A detection pipeline that fails silently is worse than none, because you trust the quiet. Grafana runs five rules against the orchestrator itself:

  • PIPE-009: a detection run recorded an error
  • PIPE-010: a sweep or drain Job crashed
  • PIPE-011: matches stuck in pending
  • PIPE-012: matches dead-lettered
  • PIPE-013: no runs recorded in 15 minutes, or the sweep is suspended or not scheduled

Grafana runs on a different node than ClickHouse, so it can keep evaluating rules if the ClickHouse node goes down. PIPE-013’s ClickHouse rule sets both execErrState and noDataState to Alerting: a failed query or missing data is itself an alert condition. What it can’t catch is losing the whole cluster, since everything watching lives inside it. An external dead man’s switch is on the list.

What’s next

Today, an alert is a Discord message, and what I decided about it isn’t recorded anywhere. The next step is to turn matches into cases with a recorded disposition, then build a fixed evidence packet for each case. After that, a model scores each case in shadow, next to my own call. Auto-closing obvious false positives only gets turned on per detection, and only after that shadow score has agreed with me often enough. Closing a case records a decision after detection; every match still goes through the Discord delivery path. No model call will delay or suppress that alert.

I also plan to add runbook_url to the detection YAML, so an agent can follow the investigation steps when a detection triggers.

After that comes hunting: a relaxed version of each detection with its exclusions removed, to see what the tuning is hiding.

What about streaming detections? 👀 Unlikely for now, a more difficult problem to solve.
